## 2. Failure analysis

The single first-run failure was an **incorrect expectation in the test, not an API regression**: the "empty request body" test expected 500 based on an earlier exploratory probe made with Node's raw `fetch`, but through Playwright's request context the API answers 400. The expectation was corrected to the behaviour at the boundary the test actually uses, and the client-dependent difference was documented in `negative-testing.md` (note on case #15).

## 4. Defects

Six deviations from HTTP/REST conventions were reproduced and documented in [defect-samples.md](defect-samples.md):

| ID          | Summary                                                      | Severity |
| ----------- | ------------------------------------------------------------ | -------- |
| DEF-API-001 | Failed authentication returns 200 instead of 401             | Major    |
| DEF-API-002 | Successful DELETE returns 201 Created                        | Minor    |
| DEF-API-003 | PUT/DELETE on nonexistent bookings return 405 instead of 404 | Minor    |
| DEF-API-004 | Missing mandatory fields crash with 500 instead of 400       | Major    |
| DEF-API-005 | Wrongly typed price silently stored as null                  | Major    |
| DEF-API-006 | Invalid dates stored as `"0NaN-aN-aN"`                       | Major    |

The automated suites assert these actual behaviours, so a future fix on the API side will surface as a test failure and a prompt to update both the tests and the defect records.

## 7. Recommendations

1. If the API were owned by the team, prioritise DEF-API-004/005/006 — input validation gaps that crash the server or corrupt data.
2. Add contract tests for the XML content-type variant the API also advertises.
3. Consider a scheduled CI run (cron) to detect behaviour changes of the public instance early.
